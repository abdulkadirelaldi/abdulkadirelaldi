### B — P2003 alan ipucu · **Backend** · ölçüm Backend'in gerekçesini çürüttü

Güvenlik BULGU-022'de alan ipuçlu `VALIDATION_ERROR` istedi; sen `VALIDATION_ERROR`
verdin ama `fields` boş bıraktın. Gerekçen şuydu:

> *"Prisma'nın `meta.field_name`i kısıt adını taşıyor (`post_coverAttachmentId_fkey`),
> form alan adını değil. Profilde iki eklenti alanı var — sezgiselle yanlışını
> işaretlemek, hiç işaretlememekten kötü olurdu."*

**Canlı ölçtüm** (DB'yi kaldırdım, gerçek FK ihlali, geri alınan işlem):

```
code: P2003
meta: { "modelName": "Profile",
        "driverAdapterError": { "cause": {
          "originalCode": "23503",
          "kind": "ForeignKeyConstraintViolation",
          "constraint": { "index": "profile_avatarAttachmentId_fkey" } } } }
```

`meta`'da **`field_name` hiç yok.** Kısıt adı `meta.driverAdapterError.cause.constraint.index`
altında, iç içe. Ve **kısıt adı alan adını içeriyor**: `profile_avatarAttachmentId_fkey`
→ `avatarAttachmentId`. Ayrıştırması mekanik: `<tablo>_` ön ekini ve `_fkey` son ekini
sıyır. **Bu bir sezgisel değil, belirlenimci bir eşleme** — yanlış alanı işaretleme
riski yok.

Dört kısıdın hepsi aynı biçimde:
`post_coverAttachmentId_fkey` · `project_coverAttachmentId_fkey` ·
`profile_avatarAttachmentId_fkey` · `profile_cvAttachmentId_fkey`

**Yani kararın yanlış olabilir ama gerekçen kesinlikle yanlıştı.** Gerçek takas şu:
kabuk **sürücü bağdaştırıcısına özgü ve iç içe** — Prisma'nın belgelenmiş hata
sözleşmesinin parçası değil, bağdaştırıcı sürümüyle değişebilir.

- [ ] **Yeniden karar ver, ölçülen kabukla.** İki yol da savunulabilir:
      doldurmak (kullanıcı hangi alanı düzelteceğini görür) ya da boş bırakmak
      (belgelenmemiş bir kabuğa bağlanmamak). **Kararı sen ver, gerekçesini yaz.**
- [ ] Dolduruyorsan: kabuk değişirse **sessizce boş `fields`'a düşmesin** — kabuğun
      beklendiği gibi olduğunu ölçen bir test, ve bulunamazsa gürültülü davranış
- [ ] Doldurmuyorsan: gerekçe **"belgelenmemiş kabuk"** olarak yazılsın, "sezgisel"
      olarak değil — ve `fields`'ın neden boş olduğu kullanıcıya dönen mesajda
      telafi edilsin (bugünkü metin bunu zaten yapıyor)

### C — `MDX_OPTIONS` tek kaynağa taşınsın · **Frontend**

Backend çiftlenmeyi kaldırmayı denedi ve **ölçülen bir duvara çarptı**:

```
Failed to parse source for import analysis because the content contains
invalid JS syntax … src/components/public/mdx.tsx:80:6
```

`MDX_OPTIONS` bir `.tsx` modülünde. Oradan içe aktarıldığında Vitest'in `unit`
projesi (`environment: 'node'`, React eklentisi yok) `mdx-validate.ts`'i ve onu
içe aktaran dört eylemi **hiç yükleyemiyor**. Üretim sınırı değil, test altyapısı
sınırı — ama bağlayıcı.

Backend yeni bir tanım **açmadı** ve doğru yaptı: `src/lib/mdx-options.ts` açıp
oradan okumak üçüncü bir kopya doğururdu ve hiçbiri kanonik olmazdı.

- [ ] `MDX_OPTIONS` **`src/lib/mdx-options.ts`'e taşınsın** (JSX'siz `.ts` modül)
- [ ] `mdx.tsx` oradan içe aktarsın — **kanonik tanım orada, kopya kalmasın**
- [ ] **Dosya sahipliği:** `src/lib/` kökü §10.1'de atanmamış. Bu dosyayı sana
      veriyorum (kanonik tanımı `mdx.tsx` yapıyordu). Tek seferlik atama, §10.1
      değişikliği değil.
- [ ] Backend'in notu: `as const` **konulamadı** — `SerializeOptions` değiştirilebilir
      dizi (`Pluggable[]`) istiyor. Taşırken aynı duvara çarpmayın.

Taşındıktan sonra Backend çiftlenmeyi kaldırır ve kapının yarı-açık dalı kapanır.
**Backend'in `toContain('MDXRemote')` iddiası** da o turda `compileMDX`'e çevrilecek —
Frontend haklı: iki taraf da artık `compileMDX` kullandığı için eşdeğerlik daha güçlü.
